# M2: window management, clipboard, cursor, scaling, metrics

Status: **M2.1 (mini-WM / popups), M2.2 (clipboard), M2.3 (cursor) and M2.5
(metrics HUD) implemented.** M2.4 (scaling) is deferred: no current need, and
fit/zoom would blur text and complicate pointer mapping.

## M2.1 Mini-WM / popups

### Protocol (PROTO_VERSION 3)

`WindowCreate` now carries:

| Field | Meaning |
|---|---|
| `kind` | `KIND_NORMAL`, `KIND_DIALOG`, `KIND_MENU`, `KIND_TOOLTIP`, `KIND_UTILITY`, `KIND_SPLASH`, `KIND_OTHER` |
| `parent` | `WM_TRANSIENT_FOR` (0 = none) |
| `override_redirect` | app-managed (menus/tooltips): never steal input focus |

Classification lives in `xcom-x11/src/windows.rs::window_info`:

- `_NET_WM_WINDOW_TYPE` → dialog / menu / dropdown/popup menu / combo / tooltip /
  utility / toolbar / splash / normal;
- `WM_TRANSIENT_FOR` → parent;
- `override_redirect` → app-managed; bare override windows are treated as
  menus;
- menus/tooltips that omit `WM_TRANSIENT_FOR` get the currently focused window
  as their parent (placement only).

### Placement and focus (client)

- Dialogs that ask for `(0,0)` are centered on their parent.
- Menus/tooltips are offset from their parent by the same delta the remote
  window has from its parent.
- Normal windows keep the usual `remote + 32` offset.
- Override-redirect windows get no decorations, are not resizable, are raised
  when mapped, but **do not** get the remote X input focus (`Message::Focus` is
  suppressed) — menus rely on the app's own grabs.
- The position used for parent-relative math is the last position we asked for
  (or the last `Moved` event): Wayland has no global window positions, so
  `outer_position()` is often unavailable there.

### Teardown fix found by the WM test

The exec'd app was started as `sh -c "<cmd>"`. Killing the `sh` child left
grandchildren (`xcomd m0 wm-demo`, `xterm & xterm & wait`) orphaned. The app is
now its own process-group leader and teardown signals the whole group
(SIGTERM, then SIGKILL after 300 ms). The e2e teardown check also looks for
`xcomd serve` only, since the app binary is named `xcomd` too.

### Tests

- `xcomd m0 wm-demo` creates a normal window, a transient dialog at `(0,0)`
  with `_NET_WM_WINDOW_TYPE_DIALOG`, and an override-redirect popup menu.
- `CHECK_WM=1 scripts/e2e-ssh.sh 5` asserts three windows with kinds 0/1/2, a
  non-zero dialog parent and `override=true` on the menu.
- Verified locally: dialog centered at `(162,132)` on a parent at `(112,92)`,
  menu placed at the parent's offset, no leftovers after the session.

### Known limitations

- On Wayland the client's windows are independent toplevels; the compositor
  may ignore position hints for dialogs/menus. On X11 and Windows the positions
  are honoured. True Wayland popups would need `xdg_popup`, which winit 0.30
  does not expose.
- Stacking among the app's windows relies on focusing/raising the popup; a
  native "always above the parent, below other apps" relation is not available.
- `_NET_WM_STATE` maximize/fullscreen hints are not handled yet; the local
  window manager's own maximize is forwarded as a resize.

## Popup fixes found while testing gtk3-demo

Right-clicking in `gtk3-widget-factory` exposed three issues:

1. **Phantom black box**: GTK maps a 1×1 INPUT_OUTPUT helper (plus 10×10
   INPUT_ONLY windows) when a menu is shown. The capture accepted every mapped
   top-level, and the client forces (normal) windows to at least 64×64, so the
   helper appeared as a 64×64 black box. Capture now ignores InputOnly windows
   and anything smaller than 8×8; the client also uses the **real size** for
   override-redirect popups instead of the 64px minimum.
2. **Popup position**: `ConfigureNotify` was only forwarded when the *size*
   changed, so toolkits that map a popup and then move it left the native
   window at the map-time position. Moves now produce a geometry event, and
   the client repositions dialogs/popups relative to their parent.
3. **XTEST buttons**: key and button events must pass `root = None` (motion
   uses the root window); the host Xvfb silently dropped button events that
   carried a root. Fixed in the injector and the test helper.

Verified with `gtk3-widget-factory`: right-clicking the text view opens a
140×159 override-redirect menu at the click position, with no phantom window;
only the input-only helper is logged as ignored.

## Popup placement: X11 and Wayland

Remote override-redirect windows (menus/tooltips) are now created as **local
override-redirect windows on X11** (`WindowAttributesExtX11::with_override_redirect`).
A window manager must not move, tile or decorate those, so our computed
position is exact under any WM. Verified with gtk3-widget-factory: the 140x159
menu lands at the click position and the local window reports
`override=true`.

Wayland has no global window coordinates and winit 0.30 does not expose
`xdg_popup`, so a native Wayland client cannot position independent toplevels.
Workaround until xdg_popup support:

```sh
env -u WAYLAND_DISPLAY xcom connect --ssh … --exec gtk3-demo
```

That runs the client on XWayland (X11 backend), where the override-redirect
path above makes popup placement exact.

## M2.2 Clipboard (text)

Protocol (PROTO_VERSION 4):

| Message | Direction | Meaning |
|---|---|---|
| `ClipboardGet { target }` | client → server | ask for the current selection |
| `ClipboardSet { target, text }` | client → server | push text; the daemon owns the selection |
| `ClipboardData { target, text }` | server → client | reply (empty = no selection) |

`target` is `CLIPBOARD_CLIPBOARD` (0) or `CLIPBOARD_PRIMARY` (1); only CLIPBOARD
has a shortcut so far. Text is capped at 60 KB (`MAX_CLIPBOARD_TEXT`).

### Server

`xcom-x11/src/clipboard.rs` runs a worker thread with its **own X connection**
and a 1x1 selection-owner window:

- `get`: classic `convert_selection` round trip (UTF8_STRING, then STRING),
  answering any concurrent `SelectionRequest` while it waits.
- `set`: takes ownership and answers `TARGETS`, `UTF8_STRING`, `STRING` and
  `TEXT` requests from remote applications.
- The session works without it (spawn failures are logged and disabled).

### Client

Local shortcuts (intercepted, not forwarded):

- **Ctrl+Shift+C** — copy the remote selection to the local clipboard.
- **Ctrl+Shift+V** — push the local clipboard to the remote; the app's normal
  paste shortcut (Ctrl+V) then finds it.

`arboard` (text only, image features disabled) reads/writes the local
clipboard. On Linux without the Wayland data-control feature it uses X11; under
KDE the XWayland clipboard is synchronised with the Wayland one.

### Tests

- `cargo test -p xcom-x11 --test clipboard`: an external owner → worker.get and
  worker.set → external reader, against a private Xvfb.
- `scripts/e2e-clipboard.sh`: remote selection → local clipboard via
  Ctrl+Shift+C, then local clipboard → remote via Ctrl+Shift+V, with the client
  on a private Xvfb (X11) and the daemon in the test container.

### Caveats

- Synchronisation is explicit (shortcuts); the clipboards are not mirrored in
  the background.
- PRIMARY is defined on the wire but has no client shortcut yet.
- Text only (no images/HTML), 60 KB cap.
- The remote app pastes with its own shortcut; the client only publishes the
  selection.

## M2.3 Cursor sync

- The capture session selects XFixes cursor input on the root. It queues the
  **initial** pointer image at connect and a fresh image on every
  `CursorNotify` (deduplicated by `cursor_serial`).
- `Message::Cursor` (control channel) carries hotspot, size and ARGB
  premultiplied pixels; dimensions above 128x128 are ignored (the control
  frame limit is 128 KiB).
- The client converts premultiplied ARGB to straight RGBA (winit's
  `CustomCursor::from_rgba`) and creates the cursor through the event loop. It
  is applied to every open window and to windows opened later. Winit 0.30
  supports custom cursors on Wayland as well as X11/Windows.
- The pointer is display-global, so one cursor is mirrored at a time (not
  per-window).

Verified: the initial 16x16 cursor plus the xterm I-beam (`9x16`, hotspot
`(4,8)`) reach the client; `m0 selftest` asserts the initial image and a cursor
change (16x16) after a pointer warp.

**Root cursor**: a bare X server has no desktop to set a root cursor, so it
keeps the classic X glyph. GTK does not set a cursor for plain widgets; they
inherit the root, which is why gtk3-demo showed a big X everywhere except over
text. When the daemon owns the display (`--display` is not used), capture now
sets the classic left_ptr arrow (`create_glyph_cursor`) on the **long-lived
capture connection** (X frees resources of the temporary setup connection,
which would reset the root). Xcursor theme resources are also published on the
root for libXcursor clients.

`XCOM_DEBUG` dumps every received cursor: an ASCII alpha mask plus a PPM
(`--dump-ppm` base or `/tmp/xcom-cursor*.ppm`) — this is what identified the
I-beam and the root X.

## M2.5 Metrics HUD

Server-side counters are reported over the control channel ~1 Hz as
`Message::Stats` (`MSG_STATS`, protocol 6): frames, rects, raw/compressed
bytes, mean capture and encode time (from `FrameStats`), and the number of
tracked windows. Counting happens in `serve_loop`, including the full captures
sent on map/resize, so the compression ratio reflects everything on the wire.

The client combines that with its own accounting (bytes and frames seen on the
bulk channel) and a ping/pong round-trip:

- `rtt` — the client pings immediately and then every 5 s (the keepalive now
  lives in the control loop). `t` is echoed verbatim, so it works across hosts
  whose clocks are unrelated.
- `fps` — client-side frame rate; `srv-fps` is the server's own report.
- `rx` — compressed bytes/s over the bulk channel; `x…` is the compression
  ratio (server counters).
- `cap`/`enc` — server capture and LZ4 encode time per frame.
- `in->px` — time from the last input we sent to the next frame presented for
  that window (local monotonic clock only).
- `pres` — total presents.

Rendering is dependency-free: `crates/xcom-client/src/hud.rs` embeds the
public-domain 8x8 `font8x8` bitmap font (Daniel Hepper) and draws a translucent
panel, four text lines and a bandwidth sparkline **into the presented surface,
never the pixel store** — the overlay cannot be mistaken for remote content.
`egui` was rejected: it has no software renderer, so it would need a GL/`wgpu`
backend or a hand-written rasteriser, and its post-0.35 font stack
(`vello_cpu`/`skrifa`/`harfrust`) is several times larger than this whole HUD.

Enable with `--hud`, toggle in-session with **Ctrl+Shift+M** (never forwarded).
`about_to_wait` requests redraws every 500 ms while the HUD is on, so the rates
stay live even when the remote window is static.

Tests: `hud.rs` unit tests (font coverage, glyph pixels, clipping, empty HUD);
`Message::Stats` is in the protocol round-trip test; `scripts/e2e-direct.sh`
runs with `--hud` and asserts the metrics line, plus
`check-ppm.py … hud` verifies from the screen readback that the overlay and the
sparkline are present in the corner and that nothing leaks outside it.

## Capture robustness: windows disappearing mid-frame

A window can be destroyed or unmapped between its `DamageNotify` and our
`ShmGetImage`; the named pixmap then reports `BadDrawable`. Those rectangles
are now skipped quietly (debug log only) instead of being reported as capture
failures — the window is disappearing anyway. Real errors (e.g. `BadMatch`
from an undersized SHM segment) still log loudly.

On unmap/remap the named backing pixmap can be invalidated, so it is
re-`NameWindowPixmap`'d before the remap is announced; the full capture that
follows then reads a valid pixmap.
