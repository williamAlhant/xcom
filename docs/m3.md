# Persistent sessions (M3)

A session now outlives the client that created it. Closing the laptop, losing
the network or killing the client leaves the remote app running; reattaching
under the same name re-shows it. The app still defines the session's life: when
the app process exits, the session ends.

## Using it

```sh
# create/attach a named session (same command either way)
xcom connect --ssh user@host --session work --exec 'xterm'

# the client is gone, the app is not
xcom sessions --ssh user@host
xcom connect --ssh user@host --session work      # reattach

# end it (kills the app and Xvfb)
xcom kill --ssh user@host --session work
```

- The name defaults to `default`. Names are scoped to the remote user and live
  under `$XDG_RUNTIME_DIR/xcomd/` (fallback `/tmp/xcomd-<uid>/`).
- `--replace` tears an existing session down and starts a fresh one. It is the
  way to change `--exec` or `--spawn` on an existing name.
- `--idle-timeout N` ends a session after N seconds without a client. The
  default is 0 (never), so an overnight lid-close survives; use `xcom kill`.
- A second client while one is attached is rejected as "session busy". There is
  no stealing and no multi-client sharing.
- `--direct` keeps the old one-shot `xcomd serve` behaviour and cannot reattach:
  its single-use tokens only arrive over ssh.

## Closing the last window

Closing a non-last window sends `WM_DELETE_WINDOW` to that app window, as
before. Closing the **last** attached window asks what you meant, with an
in-window dialog:

| button | effect |
|---|---|
| Close window | app quits, session ends |
| Disconnect (focused) | client exits, session and app keep running |
| Cancel | dialog closes; Esc and a click outside do the same |

Tab/Left/Right move focus, Enter/Space activate, the mouse hovers and clicks.
While the dialog is up it consumes input locally; the remote app never sees it.
Scripts and tests use `--close-action close|disconnect` to skip the dialog.

## How it works

### Owner and attachments

`xcomd session` is the **owner**: it owns Xvfb, the app child, the capture
session, the keymap, geometry and the clipboard worker. An **attachment** is one
client connection: two TLS channels, a control thread and a capture loop. The
owner loop is:

```
wait for attach -> prepare tokens/acceptor -> hand over handshake
                 -> accept TLS -> resync -> serve until detach -> repeat
```

While detached the owner drains the capture session and drops frames; there is
no backlog. The clipboard worker is spawned once and keeps owning the remote
selection, so paste inside the app still works while no client is connected.

### Rendezvous and trust

The owner listens on `$XDG_RUNTIME_DIR/xcomd/<name>.sock` (directory 0700, socket
0600). `xcomd attach` (the process sshd starts) speaks one JSON line over it:

```
{"cmd":"attach","peer":"203.0.113.7"}   -> {"ok":true,"proto":7,...}
{"cmd":"info"}                         -> session description
{"cmd":"kill"}                         -> {"ok":true}
```

`attach` reads `SSH_CONNECTION` itself and forwards the peer IP. The owner uses
it for the TLS allowlist and the address advertised to the client. The detached
owner's inherited `SSH_CONNECTION` is deliberately not used: it would pin the
first laptop's address forever.

On `--create` (or when the socket is missing and `--create` was passed), attach
spawns `xcomd session` with `setsid`, stdin `/dev/null` and stdout/stderr to
`<name>.log`, waits for the socket, then places the attach request. The owner
returns a fresh handshake over the socket; the bootstrap prints it on stdout and
exits, so ssh sees EOF immediately. Each attachment gets fresh single-use
control/bulk tokens and a fresh ephemeral certificate.

The handshake keeps the old fields and adds `session_name`, `created`,
`attached` and `app` (the command line, so a reattach can say what is running).

### Detach and resync

A clean `Bye`, EOF, a crash or 30 s of silence ends the attachment, not the
session. On the way out the control loop releases every key and button it saw
pressed (XTEST state is global to the display) and the owner clears the busy
flag. On the next attach:

- the window list and a full frame per window are sent again (`announced` is
  reset),
- the cursor image is force-refreshed (`refresh_cursor`, because the serial
  check would otherwise suppress an unchanged cursor),
- the client re-reads the clipboard with `ClipboardGet`,
- metrics, focus and the cursor shape are rebuilt from scratch.

The session ends when the app child exits, on `xcomd kill`, or when an idle
timeout elapses while detached. The socket file is removed on exit; a stale
socket from a killed owner is replaced by the next session.

## Testing

`scripts/e2e-persist.sh` runs three clients against the test VM: create, detach,
reattach (same display and app pid), the close dialog's Disconnect, a SIGKILLed
client releasing a held key, and `kill` tearing down app + Xvfb. Clients run on
a private Xvfb so synthetic focus cannot race the developer's desktop.
`x11_input` gained `close`, `keystate` and already had `focus`/`down`/`up` for
this.

## Known limitations

- One attachment per session.
- Reattach is manual; automatic reconnect after a dropped link is the next
  milestone.
- `--idle-timeout` is only applied at creation; changing it needs `--replace`.
- `xcom sessions`/`kill` need ssh; there is no local socket client yet.
- The owner is a normal user process: it does not survive a reboot, and there is
  no systemd --user unit yet.
